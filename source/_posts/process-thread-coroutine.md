## 一、面试时怎么回答？

进程、线程、协程的区别，主要体现在资源隔离、调度方式和并行能力上。

- **进程**是操作系统进行资源分配和隔离的重要单位，通常拥有独立的虚拟地址空间。多进程可以利用多个 CPU 核心，但创建、通信和数据传递的成本通常较高。
- **线程**是操作系统调度 CPU 执行的基本单位之一。同一进程内的线程共享地址空间和多数资源，每个线程有自己的栈和执行状态。线程之间通信方便，但共享数据需要同步。
- **协程**是一种可以暂停和恢复的执行方式。以 Python `asyncio` 为例，事件循环在一个线程内协作调度多个任务：任务等待异步 I/O 时可以让出执行机会，从而提高等待时间的利用率。

结合 Python 来说，在常见的启用 GIL 的 CPython 中，CPU 密集型的纯 Python 任务通常考虑多进程；阻塞式 I/O 可以使用线程池；支持异步调用的大量网络 I/O 可以使用协程。

在 Agent 开发中，LLM API、搜索和远程数据库调用通常包含较多网络等待，因此适合考虑异步并发；本地大量计算需要单独分析，不能仅靠增加协程加速。

> 关键边界：多线程并非天然不能并行，协程也不等于异步 I/O。讨论具体行为时，需要说明语言、运行时和执行方式。

## 二、先区分并发与并行

**并发**：多个任务在一段时间内交替推进，不要求同一时刻执行。

**并行**：多个任务在同一时刻执行，通常需要多个 CPU 核心等执行资源。

例如：

- 一个 CPU 核心轮流执行多个线程，可以形成并发。
- 多个 CPU 核心同时执行不同进程或线程，可以形成并行。
- 单线程事件循环处理多个异步网络请求，可以形成并发，但这些协程中的 Python 代码不会因此在多个核心上同时执行。

因此，**并发强调任务如何组织和推进，并行强调是否同时执行**。

## 三、核心区别对照

以下协程特指 Python `asyncio` 的典型使用方式。

| 对比维度 | 多进程 | 多线程 | 协程 |
|---|---|---|---|
| 执行载体 | 多个进程，每个至少包含一个线程 | 一个进程内的多个线程 | 通常是一个线程内的多个异步任务 |
| 调度方式 | 操作系统调度进程中的线程 | 操作系统调度 | 事件循环协作调度 |
| 内存关系 | 默认地址空间相互隔离，可显式共享 | 共享进程地址空间 | 同一线程内的任务共享所在进程的内存 |
| 独有状态 | 进程资源、地址空间等 | 线程栈、寄存器状态等 | 挂起位置、局部变量等协程状态 |
| 创建和切换成本 | 通常较高 | 通常低于进程，但仍有系统调度成本 | 通常较低，适合大量等待型任务 |
| 数据交换 | 队列、管道、共享内存等 | 共享对象，配合锁等同步机制 | 参数、共享对象、异步队列等 |
| 多核并行 | 可以 | 可以，但受运行时和任务类型影响 | 单线程事件循环本身不提供多核并行 |
| 主要风险 | 通信、序列化、内存和管理成本 | 数据竞争、死锁、线程数量失控 | 阻塞事件循环、任务堆积、取消处理不当 |
| 常见场景 | CPU 计算、进程隔离 | 同步 I/O、阻塞 SDK | 异步网络请求、高并发 I/O |

> 开销大小是一般趋势，实际效果取决于任务粒度、数据规模、操作系统和实现方式，需要通过测量判断。

### 1. 多进程：资源隔离更明确

不同进程通常拥有独立的虚拟地址空间。

因此，在子进程中修改一个普通 Python 列表，不会自动修改父进程中的列表。需要通过队列、管道、共享内存等方式交换数据。

多进程的优势：

- 可以利用多核执行 CPU 密集型任务。
- 地址空间隔离较强，有助于划分故障边界。

对应的代价：

- 启动进程和管理生命周期需要成本。
- 传递 Python 对象时，常涉及序列化和复制。
- 多个进程分别加载大型模型或数据，可能显著增加内存占用。

因此，小任务不一定适合多进程：计算节省的时间可能抵不过启动和通信成本。

### 2. 多线程：共享资源方便，同步更复杂

同一进程内的线程可以访问共享对象，因此传递数据通常比较方便。

但“共享”也意味着多个线程可能同时修改同一份状态。例如：

1. 线程 A 读取当前余额。
2. 线程 B 也读取当前余额。
3. 两个线程分别计算并写回结果。
4. 后写入的结果覆盖前一个结果。

这类问题需要使用锁、队列或其他同步机制协调。

另外，一个线程发生普通 Python 异常，通常不会直接终止整个进程；但进程级崩溃可能影响其中所有线程，线程不能提供进程级隔离。

### 3. 协程：在等待时推进其他任务

协程适合解释成“可以暂停并继续执行的函数”。

在 `asyncio` 中，协程通常被包装成 Task，由事件循环调度。当任务等待尚未完成的异步操作时，可以挂起自己，让其他就绪任务执行。

这里有两个关键点：

- **协作调度**：任务需要在适当位置交还执行机会，长时间计算会占住事件循环线程。
- **`await` 不保证一定切换任务**：如果等待的对象已经就绪，执行可能直接继续。

协程减少的是大量等待型任务所需的调度和资源成本，不会让 CPU 计算自动变快。

## 四、为什么 Python 多线程经常被说“不能并行”？

这句话省略了适用条件。

更准确的说法是：

> 在常见的启用 GIL 的 CPython 中，同一解释器内，同一时刻通常只有一个线程执行 Python 字节码，因此多线程通常无法加速 CPU 密集型的纯 Python 计算。

### GIL 不妨碍线程处理很多 I/O 场景

线程等待网络、文件等 I/O 时，相关实现通常会释放 GIL，让其他线程执行。

因此，多个线程可以重叠处理多个请求的等待时间。

### 原生扩展可能释放 GIL

某些原生扩展会在计算期间释放 GIL，这时线程可能实现计算并行。需要结合具体库和操作判断，不能只看“代码是不是用 Python 调用”。

### Free-threaded CPython 需要单独讨论

从 Python 3.13 开始，CPython 提供可禁用 GIL 的 free-threaded 构建。

因此，面试时应明确自己讨论的是哪种解释器和构建方式，避免说“Python 多线程永远不能并行”。

### GIL 不等于业务线程安全

即使启用了 GIL，包含多个步骤的业务操作也可能被线程切换打断。

“检查库存再扣减”“读取余额再更新”等逻辑，仍然需要适当同步。

## 五、Agent 开发中怎么选？

选型前，先判断任务的主要耗时来自哪里。

| Agent 场景 | 可以优先考虑 | 判断依据 |
|---|---|---|
| 调用多个相互独立的 LLM API | 协程 | 主要等待网络，且客户端支持异步 |
| 并发搜索多个数据源 | 协程 | 请求相互独立，能够重叠等待 |
| 调用只有同步接口的工具 SDK | 线程池 | 把阻塞调用移出事件循环线程 |
| 批量执行耗时的纯 Python 计算 | 进程池 | 可能需要绕过 GIL，利用多核 |
| 本地模型推理 | 结合推理框架判断 | 受 GPU、批处理、显存和原生实现影响 |
| 执行不可信代码 | 独立沙箱方案 | 需要权限、文件系统、网络和资源限制 |

> 独立进程只提供部分隔离能力，不能直接当作安全沙箱。

### 并发前先检查任务依赖

假设 Agent 要完成：

1. 搜索天气。
2. 搜索交通。
3. 根据两者生成出行建议。

天气和交通查询可以并发，但生成建议需要等待查询结果。

相反，如果第二次工具调用的参数依赖第一次调用的返回值，就不能直接同时执行。

**任务之间是否独立，是并发能否成立的前提。**

### 并发不等于无限创建任务

实际项目还要控制：

- 并发请求数量。
- API 的 RPM、TPM 等配额。
- 单次调用超时。
- 重试次数和退避策略。
- 用户取消后的任务清理。
- 重试写操作时的幂等性。

其中，**限制同时运行的请求数，不等于限制每分钟请求数或 Token 数**。信号量负责并发控制，速率配额还需要相应的限流机制。

## 六、代码示例：并发调用独立工具

下面用异步等待模拟工具请求，重点观察任务调度方式。

示例使用 Python 3.11+ 的 `TaskGroup`。

```python
import asyncio
from time import perf_counter


async def call_tool(name: str, delay: float) -> str:
    # 模拟支持异步等待的网络调用
    await asyncio.sleep(delay)
    return f"{name} 完成"


async def main() -> None:
    semaphore = asyncio.Semaphore(2)

    async def run_one(name: str, delay: float) -> str:
        async with semaphore:
            async with asyncio.timeout(5):
                return await call_tool(name, delay)

    started = perf_counter()

    async with asyncio.TaskGroup() as group:
        tasks = [
            group.create_task(run_one("搜索天气", 1)),
            group.create_task(run_one("搜索交通", 1)),
            group.create_task(run_one("搜索酒店", 1)),
        ]

    print([task.result() for task in tasks])
    print(f"耗时：{perf_counter() - started:.2f} 秒")


if __name__ == "__main__":
    asyncio.run(main())
```

三个任务各模拟等待 1 秒，最多同时执行两个，因此理想情况下总耗时约为 2 秒。

注意：

- `asyncio.sleep()` 只是模拟异步等待，并没有真正调用工具。
- 实际接入时，应使用支持异步调用的客户端。
- 这个信号量只约束共享它的这些任务，不是整个服务的全局限流器。
- timeout 在取得信号量后开始计时，不包含排队等待的时间；需要端到端超时时，应调整超时范围。
- 示例适合少量任务；海量输入还应使用有界队列和固定数量的 worker，避免一次创建过多 Task。

### 为什么不直接连续写三个 `await`？

```python
weather = await call_tool("搜索天气", 1)
traffic = await call_tool("搜索交通", 1)
hotel = await call_tool("搜索酒店", 1)
```

这段代码在异步函数内执行时，会依次等待三个调用完成，总耗时约为 3 秒。

**`await` 表示等待一个可等待对象；要让多个独立操作并发推进，还需要通过 Task、TaskGroup 等方式组织执行。**

### 同步工具能否直接放进 `async def`？

不能因为外面加了 `async def`，就认为内部调用变成了非阻塞操作。

例如：

```python
async def bad_tool():
    # time.sleep() 会阻塞当前事件循环线程
    import time
    time.sleep(2)
```

对于适合在线程中执行的阻塞式 I/O，可以考虑：

```python
result = await asyncio.to_thread(sync_tool, argument)
```

前提是该工具适合在线程中调用，并且需要控制线程池容量。

另外，取消等待或触发超时，通常不会强制停止已经在线程中运行的同步函数，因此底层客户端本身也需要配置超时。

## 七、面试常见追问

### 1. 单核 CPU 上，多线程还有意义吗？

有。

虽然不能在多个核心上同时执行，但当一个线程等待 I/O 时，可以调度其他线程，改善吞吐和响应性。

如果全是 CPU 计算，多线程可能因为额外调度和同步而变慢。

### 2. 单线程协程需要锁吗？

有时需要。

如果“读状态、等待、写状态”的过程中存在挂起点，其他任务可能插入执行，导致逻辑竞争。

这时可以考虑 `asyncio.Lock`，但不能让它替代数据库事务、跨进程锁等其他层面的协调机制。

### 3. 一个协程失败，其他协程会怎样？

取决于任务组织方式。

在 `TaskGroup` 中，一个任务发生普通未处理异常时，通常会取消组内其他未完成任务，等待清理后再报告异常。

如果工具调用允许部分失败，应明确设计错误处理和结果结构，避免无意中让一个工具的失败取消整个步骤。

### 4. 多进程、多线程、协程可以混用吗？

可以。

例如一个服务可以：

- 使用多个进程处理请求。
- 每个进程使用事件循环处理异步 I/O。
- 使用线程池兼容同步工具。
- 把适合并行的重计算交给进程池或独立计算服务。

但资源预算需要整体计算：每个进程都创建线程池和连接池时，总连接数、线程数和内存占用会叠加。

## 八、面试速记

> 进程侧重资源隔离，线程共享进程资源并由操作系统调度；Python asyncio 协程由事件循环协作调度，适合重叠异步 I/O 的等待时间。选择时先看任务瓶颈和依赖关系，再考虑 GIL、库的能力、通信成本以及并发限制。
