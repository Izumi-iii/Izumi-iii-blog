## 一、面试回答：取消必须传到真正的生产者

SSE 是服务器持续向客户端发送事件的一种响应形式，不负责替业务取消模型任务。浏览器关闭后，后端需要检测连接中断，取消这次请求绑定的生成任务，关闭上游模型流，并清理队列、工具任务和并发额度。

**停止向浏览器发送，不等于模型已经停止生成。** 只跳出 SSE 转发循环，如果后台生产者仍在读取模型输出，Token 消耗还可能继续。

对于远程模型，断开流是否停止服务端推理、按什么口径计费，取决于提供方；若有明确取消接口，应结合任务 ID 调用。对于本地推理，应把取消传给推理引擎，让它终止对应请求。不能承诺关闭页面后“零额外 Token”。

## 二、完整链路：从断连到释放资源

可以把一次请求看成：浏览器连接 → SSE 响应任务 → 模型读取任务 → 远程接口或本地推理。每一层都应知道自己归属哪次 generation_id。

**1. 识别断连。** ASGI 提供 `http.disconnect` 事件；发送到已断开的连接也可能触发异常。FastAPI/Starlette 的具体处理会随框架及 ASGI 版本变化，需要核对实际版本和断连测试。

若使用框架响应封装，遵循它的取消机制；需要显式监听时，统一协调请求事件的消费者，不让多个任务无序竞争底层 `receive()`。

**2. 取消请求内任务。** 让模型读取、转发和断连监听处于可管理的任务生命周期中。断连后取消读取任务，并等待其退出；不要用无人管理的 `create_task()` 把模型请求留在后台。

异步取消是协作式的，通常在等待点生效。同步 SDK 放在线程里，不意味着取消等待就能杀掉运行中的线程，所以应优先采用支持取消和超时的异步流。

**3. 清理上游与状态。** 在 `finally` 或异步上下文管理器中关闭模型流和连接，释放信号量，取消工具子任务，并把生成状态标记为 cancelled。若捕获取消异常用于记录，清理后继续传播，不要吞掉后继续生成。

AnyIO 的取消作用域中，异步清理可能再次被取消，必要时使用有短超时的 shield 保护清理；不能无限保护而导致连接迟迟不退出。

## 三、一个实际设计：断连与显式停止互补

假设接口 `/chat/stream` 创建 generation_id，同时登记当前用户、会话、所属 worker、状态和取消句柄。

- 正常流程：模型片段进入有界队列，再转发为 SSE 事件；完成后写入完整回答并标记 completed。
- 页面关闭：连接断开信号触发取消路径，清理当前生成，把已产出的内容保存为部分结果，而不是完整成功答案。
- 点击停止：前端主动中断请求，并可调用鉴权后的停止接口；后端按 generation_id 找到任务执行相同的取消路径。
- 网络失联：断开不一定立即可见，增加心跳、写入超时、总生成超时和输出上限作为兜底。

**多 worker 时，取消句柄在原进程里。** 如果停止接口落到另一个 worker，仅查全局字典找不到任务。可通过共享任务注册表定位所属 worker，再用消息通道通知；真正执行取消的是拥有该任务的进程。

反向代理也会影响链路：如果浏览器到代理已断，但代理仍保持上游，应用未必立即感知。应核对代理的缓冲、超时和客户端断连处理。SSE 心跳能辅助保持活性和暴露连接问题，但不能保证瞬时检测。

用户关闭页面时的卸载回调不可靠，不能把停止完全寄托于浏览器发出最后一次请求。也要避免自动重连再次创建生成任务：恢复传输与重新生成应分开设计，并使用请求幂等标识。

## 四、三个高频追问

**Q1：在每次 yield 前判断断连够不够？**

不一定。如果模型迟迟没有返回第一个片段，代码一直等在上游读取，下一次判断根本不会执行。应具备等待期间也能生效的取消机制，并配置合理超时。具体由响应框架还是显式监听实现，需要结合实际版本验证。

**Q2：关闭上游 HTTP 流就一定能停止计费吗？**

不能保证。它停止本地接收并通知连接关闭，但远程服务可能已经生成了更多片段，或采用不同计费规则。使用提供方支持的中止机制，并记录取消时间、最后接收时间及可获得的 usage，才能验证节省效果。

**Q3：怎样证明取消实现有效？**

测试首片段前、生成中、工具执行中和网络异常四种中断。观察取消后任务数、连接数、队列和并发额度是否恢复，再结合提供方 usage 或本地推理活跃请求确认生产停止；仅看浏览器不再显示文字是不够的。

本文是工程方案，未对某个具体 SDK 的取消和计费行为作运行验证。面试中应说明实际使用的框架、模型接口以及已经做过的中断测试。
